# 28 — Inconsistent failure-code → HTTP status mapping idioms

**What's wrong:** Two admin routes map a typed failure code to an HTTP status, but they use two different idioms. The approve route uses an explicit `STATUS_BY_CODE` record keyed by code; the retract route uses an inline ternary on `result.code`. Same concern, two shapes — and the ternary form has no compile-time exhaustiveness check, so a new failure code silently maps to the default 400.

**Evidence:** `app/src/app/api/admin/leads/[id]/approve/route.ts:7-12` —

```ts
const STATUS_BY_CODE: Record<PublishFailureCode, number> = {
  'invalid-effective-from': 400,
  'lead-not-found': 404,
  'lead-not-approvable': 422,
  'evidence-below-standard': 422,
}
```

vs `app/src/app/api/admin/rule-versions/[id]/retract/route.ts:19` —

```ts
const status = result.code === 'not-found' ? 404 : result.code === 'already-retracted' ? 409 : 400
```

The record form is exhaustive over `PublishFailureCode`; the ternary form isn't, and reads differently despite solving the identical problem.
